# Dot bridge

The bridge is optional. On a fresh install, run `dotcontrol bridge enable` once to set `dot_bridge_enabled` in the installed local configuration, restart the existing runtime, then run `dotcontrol bridge enable` again to turn the bridge on in the running service. The default installation retains 13 MCP tools. With the bridge available, MCP adds four task tools and three Events methods. A missing or unavailable vault key, or a bridge open failure, leaves the regular runtime and its 13 tools available; bridge admin operations report `bridge_unavailable`.

Run `dotcontrol bridge pair` to create a separate client credential and queue. The command prints only the pairing file path and public IDs (`client_id`, `queue_id`); it never prints the bearer token. Import the file locally into the client, then remove it when import is complete. Pairing locally authorizes the runtime's configured Dot consumer to act on that queue. Pairing grants no desktop, history, or terminal permission.

Connect the private Dot plugin, refresh its metadata, and subscribe to `dot.task.available` using the returned queue ID. Events parameters are flat: `name`, `arguments`, `delivery`, and optional `cursor`/`ttlMs`. The SDK handles the Events RPC methods and protocol metadata checks. Only a successful modern `2026-07-28` `server/discover` response advertises `capabilities.events`.

Run `dotcontrol bridge probe <client_id>` explicitly to enqueue a nonce challenge. Use `dotcontrol bridge probe <client_id> --mode answer` for the default text readiness probe. `--mode task` is reserved for a future task verification probe and remains unavailable until an authorized task proof path is implemented; there is no manual readiness setter. Through MCP, claim that job with `dot_task_claim`, then complete it with the exact requested nonce. The service checks the claim token, queue authorization, current verified callback subscription generation, and completed answer state. Expected nonce text is hashed in bridge policy; the challenge prompt remains in the encrypted queue.

The paired Bearer credential accesses `/dot-bridge/v1/status`, `GET /dot-bridge/v1/jobs` (metadata-only job list for the paired client, newest first; full `result` bodies require `GET /dot-bridge/v1/jobs/{id}`), `/jobs/{id}`, `/requests/{request_id}`, and `/jobs/{id}/cancel` on the numeric loopback listener. CLI bridge client requests use a 10s timeout, `Proxy: nil`, and refuse redirects. No client-supplied identity selects a queue. Status exposes no prompt or credential. A successful text probe enables text readiness for at most ten minutes, bounded by subscription expiry. Pause, revoke, disable, renewal, and unsubscribe invalidate or suppress readiness. Runtime restart requires a fresh subscription and probe; live claim bindings are intentionally not restored.

Regular submission requires current readiness. Task execution remains unavailable until task verification is proven: `capabilities.tasks` is false and task submissions return `task_verification_required`. A text ping establishes no evidence about cloud task execution. An authorized task verification policy and work test are required before enabling that capability.

All MCP callers sharing the authenticated installation hop act as the same configured consumer. Queue IDs and worker IDs provide no authentication by themselves. A worker ID supplies retry identity and is combined with the trusted consumer identity. This proves a round trip through the configured source, not cryptographic model or personal identity. Fixture tests provide protocol evidence only, with no real account acceptance.

Operations recheck pause, revocation, enabled state, and queue policy after queue or callback I/O. A concurrent gate change can suppress a success response even when a durable write has happened. Resolve uncertain submission through the original request ID; never replay under a new ID. Cancellation records intent and cannot prove that cloud work stopped.
